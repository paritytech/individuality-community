# Benchmarking and weights

- Parameterise weight functions instead of multiplying a fixed weight (e.g. `T::WeightInfo::foo(n)` not `T::WeightInfo::foo().saturating_mul(n)`). A parameterised benchmark captures constant overhead that does not scale with the input.
- Every weight function in a pallet's `weights.rs` must have a corresponding benchmark in that pallet's `benchmarking.rs`. When adding a new extrinsic or changing weight signatures, add or update the matching benchmark.
- When a call dispatches another call, register its weight on every branch, not just one; a missed branch under-charges. When the branch taken is determined by the call arguments (except `origin`), directly match on those arguments to charge the accurate weight, otherwise charge a benchmarked upper bound and refund the difference.
- With the two-weight-function setup (`weight` + `weight_of_authorize`), benchmark the extrinsic call directly, not `#[block]`. Use adequate sampling for heavy extrinsics rather than the defaults.
- Read the benchmarked function and identify every cost driver before writing the benchmark: each loop bound, recursion depth, and storage access whose count depends on input or chain state (call parameters, collection lengths, ring/group sizes, rounds). Each driver that varies at runtime must be a `Linear` component swept over its real production range, and the weight's shape must match the function's complexity. A driver left fixed in the benchmark but variable in production silently under-charges.
- A swept component must vary the storage *keys* its loop touches, not just the count. `n` accounts seeded in one ring charge one `RingRoots` read; in production each has its own ring and adds its full `max_size` to the PoV. Seed one key per item, then check the regenerated `r:` count scales with the component instead of staying `r:1`.
- When a cost scales with the product of two parameters (e.g. a nested loop `for a in 0..n { for b in 0..m { … } }`, costing ≈ `k*n*m`), do not use two separate `Linear` components. A separable `base + a*n + b*m` model cannot represent the `n*m` interaction, so the fitted intercept and slopes become artifacts of the benchmarked ranges. Collapse them into one component equal to the product (computed by the caller from runtime state) so the regression stays linear.
- For an extrinsic with a `Linear<_, Max>` bound, assert its worst case in the pallet's `integrity_test`: `OcwWeightBudget::from_normal_max::<T>().assert_fits("name", WeightInfo::ext(Max::get()))` (from `indiv-support`; add `authorize_ext()` when authorized, plus any per-item runtime surcharge). Use the helper, so every check holds to the same share of the block. Both dimensions matter and `proof_size` usually binds first (Normal `max_extrinsic.proof_size` ≈ 3–4 MB). Without the assertion, a runtime that sets `Max` too high fails only at runtime, where OCW transactions in the pool will drop silently.
